# AI Trading — 사업 기획 문서 (v2, 다중 거래소 전환)

지난 문서(v1) 이후로 방향을 한 번 크게 틀었다. 핵심은 세 가지다.

업비트 하나만 보던 신호 데이터 소스를 Binance, OKX, Bybit, Coinbase, Upbit을 aggregate하는 다중 거래소 구조로 넓혔고(`ccxt` 기반), 지표도 RSI/MACD/MA/거래량/호가불균형에 볼린저밴드·스토캐스틱·ADX·CCI를 추가했다. 그리고 트레이딩뷰 얘기가 나왔을 때 실제로 확인해보니 트레이딩뷰는 공개 데이터 API를 제공하지 않는다는 걸 알게 됐다. 그래서 트레이딩뷰를 시세 소스로 쓰려던 계획은 접고, 대신 사용자 본인의 트레이딩뷰 계정 알림(웹훅)을 개인 대시보드로 중계해주는 부가 기능으로 스코프를 다시 잡았다. 자동매매 실행은 여전히 업비트 한정, 본인 계정만 쓴다는 원칙은 그대로다.

결국 지금 만들고 있는 건 이런 서비스다.

> "AI가 코인을 대신 거래해주는 서비스"가 아니라,
> 전세계 가상자산 시장을 다중 거래소 데이터 + 수학적 모델 + AI로 분석해서, 매매 판단에 필요한 근거를 제공하는 SaaS.

## 0. 트레이딩뷰 API, 실제로 뭐가 되고 뭐가 안 되는지

먼저 짚고 넘어가야 할 게 있다. 트레이딩뷰는 가격, 지표 값, 과거 봉 데이터를 조회할 수 있는 공개 데이터 API를 제공하지 않는다. 최근에 바뀐 게 아니라 원래부터 그렇다. 트레이딩뷰가 공식적으로 제공하는 건 아래 세 가지뿐이고, 셋 다 "시세를 가져다 쓰는" 용도는 아니다.

| API | 용도 | 우리 서비스에 맞는가 |
| --- | --- | --- |
| Charting Library | 자체 데이터를 꽂아서 트레이딩뷰 스타일 차트 UI를 그리는 용도 | 차트 UI로는 쓸 수 있지만 신호 데이터 소스는 아님 |
| Datafeed API | 브로커/데이터 제공사가 트레이딩뷰 쪽에 시세를 공급하는 규격 | 방향이 반대라서 우리가 쓸 API가 아님 |
| Broker REST API | 브로커가 주문 라우팅을 트레이딩뷰와 연동하는 규격 | 우리는 브로커가 아니라 해당 없음 |

리테일 개발자가 실제로 쓸 수 있는 건 웹훅 알림(Webhook Alert) + Pine Script 조합뿐이다. 사용자가 트레이딩뷰 차트에서 직접 만든 지표/전략에 알림 조건을 걸어두면, 조건이 맞았을 때 지정한 URL로 JSON을 POST 해주는 기능이다. 다만 이걸 쓰려면 Essential 이상 유료 플랜(월 $15~)이 필요하고, 여기서 나오는 신호는 "트레이딩뷰가 계산한 전세계 시세 데이터"가 아니라 "내가 만든 Pine Script 조건이 맞았다"는 알림 한 건일 뿐이다.

`tradingview-screener`, `tradingview_ta` 같은 오픈소스 패키지들은 트레이딩뷰의 비공식 내부 스캐너 엔드포인트를 호출하는 방식인데, 트레이딩뷰가 공식 지원하는 게 아니라서 이용약관 위반이나 무통보 차단 리스크가 있다. 상용 SaaS의 핵심 데이터 소스로 쓰기엔 위험하다고 판단했다.

그래서 정리하면 이렇다.

- 신호 추론의 주 데이터 소스는 우리가 직접 구축한 다중 거래소 수집·지표 엔진으로 한다.
- 트레이딩뷰는 선택적 보조 신호 채널로만 쓴다. 사용자가 트레이딩뷰에서 직접 만든 전략의 공식 웹훅 알림을 받아서, 추가 입력값으로만 반영하는 정도다.
- "트레이딩뷰 데이터를 끌어다 쓴다"는 식의 표현이나 마케팅은 하지 않는다. 사실과 다르고 약관 문제도 걸린다.

### 0-1. 한 걸음 더 — 유저 본인 트레이딩뷰 계정 연동

여기서 한 걸음 더 나아가기로 했다. 트레이딩뷰 웹훅 수신을 관리자 1명 전용으로 두지 않고, 유저별로 열어주는 걸 정식 상품 기능으로 채택한다.

```
유저가 이미 트레이딩뷰 유료 플랜(Essential 이상, 본인 결제)을 갖고 있다면
        ↓
우리 사이트가 유저 전용 웹훅 URL(고유 토큰 포함)을 발급
        ↓
유저가 본인 트레이딩뷰 차트/전략의 Alert 설정에 그 URL을 등록
        ↓
유저의 Pine Script 조건이 맞을 때마다 우리 서버로 신호가 들어옴
        ↓
유저 본인 대시보드에서만 그 신호가 표시됨 (다른 유저와 섞이지 않음)
```

이게 괜찮은 이유는, 트레이딩뷰가 공식 지원하는 웹훅 알림을 각 유저가 자기 계정으로 쓰는 것뿐이기 때문이다. "트레이딩뷰 데이터를 가져다 재판매한다"는 문제가 생기지 않는다. 데이터를 우리가 소유하거나 가공하는 게 아니라, 유저가 만든 알림을 유저 본인 대시보드에 중계할 뿐이다. 지표 계산 자체는 트레이딩뷰(유저 계정)가 하니까, 이 기능만 놓고 보면 우리 개발 부담은 "수신 → 검증 → 저장 → 표시"로 비교적 가볍다.

다만 한계도 분명히 있다. 트레이딩뷰 유료 플랜이 없는 유저에게는 의미가 없는 기능이라, 핵심 상품(다중 거래소 AI 신호 엔진)을 대체하는 게 아니라 이미 트레이딩뷰를 쓰는 파워유저를 위한 PRO 이상 부가 기능으로 포지셔닝한다. 그리고 유저마다 Pine Script를 다르게 짜니까 웹훅 payload 형식이 제각각일 수 있는데, 여기 대응은 `symbol`, `action` 정도만 필수 필드로 강제하고 나머지는 유연하게 받는 방식으로 간다. 유저별 웹훅 URL에는 반드시 고유 토큰이 있어야 하고, 유출됐을 때 재발급할 수 있어야 한다. 안 그러면 다른 사람이 내 대시보드에 가짜 신호를 넣을 수 있다.

## 2. 전체 시스템 아키텍처

```
             ┌──────────────────┐
             │     사용자        │
             │ PC / 모바일 웹    │
             └────────┬─────────┘
                      │ HTTPS
                      ↓
             ┌──────────────────┐
             │   Nginx           │
             └────────┬─────────┘
                      ↓
             ┌──────────────────┐
             │ PHP API Server    │
             │ 회원/결제/권한     │
             │ 분석 결과 조회     │
             └────────┬─────────┘
                      │
       ┌──────────────┼──────────────┬──────────────┐
       ↓              ↓              ↓              ↓
   MySQL           Redis       Python Engine   (선택) TradingView
       ↑              ↑              │           Webhook Receiver
       │              │              │                │
       │              │   ┌──────────┴──────────┐     │
       │              │   │  Multi-Exchange     │←────┘ 보조 신호로만 반영
       │              │   │  Collector (ccxt)   │
       │              │   │  Binance/OKX/Bybit/ │
       │              │   │  Coinbase/Upbit 등  │
       │              │   └──────────┬──────────┘
       │              │              │
       │              │       ┌──────┴──────┐
       │              │       │ Upbit(자동매매 전용)│
       │              │       └─────────────┘
       │              ↓
       │        실시간 데이터
       ↓
분석/신호/거래 기록
```

여기서 Multi-Exchange Collector는 `ccxt`로 여러 거래소(Binance, OKX, Bybit, Coinbase, Upbit 등)에서 같은 심볼(예: BTC)의 시세·캔들·거래량을 수집하고, 거래소별 지표와 거래소 간 평균/합의 지표를 함께 산출하는 역할을 맡는다. 업비트는 두 가지 역할을 겸한다. 하나는 다중 거래소 수집 대상 중 하나(KRW 마켓 기준가 제공용)이고, 다른 하나는 본인 전용 자동매매 실행처다. 이 둘은 코드·자격증명 레벨에서 완전히 분리해둔다. TradingView Webhook Receiver는 선택 기능으로, 사용자가 트레이딩뷰에서 만든 Pine Script 알림을 받아 `ai_signals`의 보조 입력(`external_signals`)으로만 저장한다. 트레이딩뷰가 신뢰할 수 있는 시세 원천이 아니라 "사용자가 설계한 조건이 맞았다는 이벤트"라는 점은 UI에도 명시할 예정이다.

## 4. 다중 거래소 데이터 수집

`ccxt`는 하나의 라이브러리로 100개 이상 거래소의 REST/WebSocket을 통일된 인터페이스로 호출할 수 있게 해준다. 이걸로 아래 조합을 구성한다.

```
BTC, ETH, XRP, SOL, DOGE (초기 5종)
   × Binance / OKX / Bybit / Coinbase / Upbit (초기 5개 거래소)
```

### 거래소별로 수집하는 데이터

```
현재가 / 체결가 / 체결량 / 거래량
호가 / 매수·매도 잔량 (호가 제공 거래소만)
1분봉 / 5분봉 / 15분봉 / 1시간봉 / 4시간봉
```

### 거래소 간 정규화와 합의(Consensus)

거래소마다 유동성과 호가 구조가 다르기 때문에, 그냥 단순 평균을 내는 게 아니라 아래 흐름으로 처리한다.

```
거래소별 지표 계산 (RSI, MACD, MA, Bollinger, Stochastic, ADX, CCI)
        ↓
거래량 가중 평균 가격/지표 산출
        ↓
거래소 간 신호 방향 일치율(Consensus %) 계산
        ↓
일치율이 낮으면(예: 특정 거래소만 급등) 신뢰도 하향
```

"왜 굳이 여러 거래소를 봐야 하는가"에 대한 답이 바로 이 구조다. 특정 알트코인이 국내 거래소 한 곳에서만 튀는 것 같은 저유동성 왜곡을 걸러낼 수 있다.

### 업비트의 이중 역할

```
업비트 = 다중 거래소 중 하나 (KRW 기준가 제공, 신호 산출용)
        +
업비트 = 본인 자동매매 실행 계좌 (완전히 별도 자격증명/코드 경로)
```

## 5. AI에게 원시 데이터를 그대로 보내면 안 된다

이 원칙은 v1과 다르지 않다. Python이 먼저 다중 거래소 지표를 계산하고 정규화한 다음에 AI에게 전달한다.

```
RSI                52.31 (거래량 가중 평균)
MACD               +1234
MA5/20/60          정배열
Bollinger          중단선 상단 돌파
Stochastic %K/%D   62 / 58 (과매수 아님)
ADX                28 (추세 강함)
CCI                +140
Volume Change      +37% (5개 거래소 평균)
Exchange Consensus 82% (8개 중 6개 동일 방향 신호)
Volatility         0.84
5m Return          +0.41%
15m Return         +0.72%
```

## 6. AI는 "판단 + 설명"만 담당

전달 스키마에 `exchange_consensus`, `data_sources`(어떤 거래소 데이터로 만들어진 신호인지)가 추가된다는 점 외에는 이전과 크게 다르지 않다. AI는 반드시 JSON 형식으로 반환하도록 강제한다.

## 7. AI만 믿으면 안 된다 — Rule Engine 우선

AI를 전체 점수의 일부로만 쓰는 것도 그대로다.

```
        +
```

가중치는 대략 이렇게 잡는다 (트레이딩뷰 웹훅을 켠 경우에만 마지막 항목이 추가된다).

```
거래소 간 합의(Consensus)                20%
거래량/호가                              15%
AI                                       15%
(선택) TradingView Webhook 보조 신호      10%  ← 웹훅 미연동 시 이 비중은 기술지표로 재배분
```

## 8. 백테스트

여기서 기준을 명확히 나눠야 한다.

- 신호 검증용 백테스트: 다중 거래소 합의 데이터 기준. 전략 자체의 일반적 성능을 검증하는 용도.
- 실전 자동매매 백테스트: 반드시 업비트의 실제 수수료, 슬리피지, KRW 마켓 유동성 기준으로 돌린다. 실제로 돈이 오가는 계좌는 업비트뿐이기 때문이다.

이 두 백테스트 결과를 섞어서 마케팅하면 안 된다. "여러 거래소 합산 신호의 이론적 적중률"과 "내 업비트 계좌의 실제 수익률"은 서로 다른 숫자다.

## 14. 거래소별 API 정책 — 반드시 개별 확인

업비트 한 곳만 상대할 때보다 신경 쓸 지점이 늘어난다.

| 항목 | 확인 필요 사항 |
| --- | --- |
| Rate Limit | 거래소마다 다름 (초당 요청 수, WebSocket 채널 수 제한 등) — `ccxt`의 `rateLimit` 속성을 신뢰하되 거래소별 공식 문서로 재확인 |
| 데이터 재판매/캐시 정책 | 일부 거래소는 시세 데이터의 상업적 재배포에 제약이 있을 수 있음 — 서비스 출시 전 각 거래소 API 이용약관 확인 필수 |
| 지역 제한 | 특정 거래소는 한국 IP/사용자 접근을 제한할 수 있음 |
| 업비트 | Open API 이용약관 및 개발자센터 쿼터 준수, 상용 재판매 관련 약관 재확인 |

"단일 수집 → 다수 고객 공유" 원칙은 그대로 유지한다. 고객 1명당 거래소 API를 호출하지 않는다는 뜻이다.

```
         Binance/OKX/Bybit/Coinbase/Upbit
                    │
                단일 수집(거래소당 1커넥션)
                    ↓
                 Redis
                    ↓
             Python Engine
                    ↓
              AI Signal
                    ↓
       ┌────────────┼────────────┐
       ↓            ↓            ↓
     고객1         고객2         고객3
```

## 22. 다국어 지원 (언어팩)

업비트 한정에서 다중 거래소로 확장하는 것과 같은 맥락으로, 서비스 자체도 한국 유저 전용이 아니라 글로벌 유저를 받을 수 있는 구조로 만든다.

### 최초 지원 언어

```
한국어 (ko) — 기본값
영어 (en)
일본어 (ja)
```

### 원칙 — "3개 언어를 지원한다"가 아니라 "언어를 추가하기 쉬운 구조를 만든다"

처음부터 3개 언어만 하드코딩하면 나중에 언어를 추가할 때마다 코드를 고쳐야 한다. 그래서 이렇게 간다.

```
지원 언어 목록 자체를 설정값(config)으로 관리
        ↓
새 언어 추가 = 번역 파일 1개 추가 + 설정에 언어 코드 등록
        ↓
코드 수정 없이 언어 추가 가능
```

### 화면(Frontend)과 데이터(Backend/AI)를 분리해서 생각해야 한다

UI 텍스트(메뉴, 버튼, 안내 문구, 법적 고지 등)는 정적 번역 파일(JSON)로 관리한다. 트래픽에 영향이 없고, 미리 다 번역해두면 끝이다. 반면 AI 신호의 "근거(reasons)"/"위험요소(risks)" 문구는 OpenAI가 실시간으로 생성하는 텍스트라서 정적 번역이 불가능하다. 여기엔 두 가지 방법이 있다.

1. AI 호출 시 응답 언어 자체를 유저의 언어로 지정 (프롬프트에 `respond in {locale}` 추가) — 신호마다 언어별로 다시 생성해야 하니 AI 호출 비용이 언어 수만큼 늘어난다.
2. (권장) AI는 항상 한국어(또는 영어) 한 가지로만 생성해서 저장하고, 화면에 표시할 때만 짧은 문구 번역 API/모델로 즉석 번역한다. 원본 신호 데이터는 언어와 무관하게 하나로 유지되고, 번역은 캐싱할 수 있다.

숫자(가격, 점수, 퍼센트, 거래소 합의율 등)는 애초에 언어와 무관하므로 번역 대상이 아니다. 다만 날짜/통화 표기 형식(예: 84,300,000원 vs $61,420)은 유저의 언어/지역 설정에 따라 포맷만 다르게 보여준다.

### 유저 경험

```
- 회원가입 시 언어 선택 (브라우저 언어 자동 감지 + 수동 변경 가능)
- 언어 설정은 유저 프로필에 저장되어 다음 로그인에도 유지
- 알림(웹 Push/이메일/카카오톡/Telegram)도 유저 언어 설정을 따름
- 법적 고지 문구도 언어별로 별도 번역 (기계번역이 아니라 검수된 문구 사용 권장 — 법적 고지는 오역 리스크가 큼)
```

이 구조는 서버 아키텍처를 바꾸는 게 아니라 PHP/Frontend 레이어에 언어팩 레이어 하나를 얹는 정도라, 개발 일정에 큰 영향은 없다 (상세 일정은 §19 참고).

### 최종 판단

다중 거래소 확장은 기술적으로 무리 없는 방향이라고 본다. `ccxt`가 이미 100개 이상 거래소를 통일된 인터페이스로 지원하니, 업비트 하나만 상대하던 코드 구조를 크게 갈아엎지 않고도 거래소 어댑터를 추가하는 형태로 확장할 수 있다. 다만 트레이딩뷰를 "데이터 소스"로 삼겠다는 원래 전제는 사실과 달랐던 부분이라, 트레이딩뷰는 어디까지나 사용자 본인이 설계한 전략의 웹훅 알림을 받는 보조 채널로 두고, 실질적으로 "전세계를 아우르는" 부분은 다중 거래소 직접 수집으로 구현하는 쪽이 맞다고 판단했다.
