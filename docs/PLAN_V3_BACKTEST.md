# 기획서 v3 — 정답지에서 실험실로

> 2026-09-04 방향 전환. `README.md`(v2 사업기획) · `ROADMAP.md`(구현 이력) 와 함께 읽는다.
> v2 를 폐기하는 문서가 아니다. **v2 의 신호 서비스는 유지하고, 그 옆에 새 축을 세운다**
> (§1-2 투트랙).

## 0. 왜 바꾸는가 — 우리 자신의 측정 기록이 근거다

방향 전환의 이유를 감이나 시장 분위기에서 찾지 않는다. 지난 사흘간 `ROADMAP.md` 에
남긴 실측이 전부 같은 말을 하고 있다.

| 시도 | 무엇을 기대했나 | 실제 결과 |
| --- | --- | --- |
| Step 4 백테스트 | 룰엔진이 비용을 넘는지 | 4심볼 전부 손실. 손익비 < 1 |
| Step 16 배점표 v3 | 배점을 고치면 점수가 품질을 가르는지 | **시기마다 부호가 뒤집힘** |
| Step 14 파생 데이터 | OI·펀딩비가 정보를 더하는지 | 가격 방향 통제하면 부호 반전. 채택 안 함 |
| Step 15 김치 프리미엄 | 국내 특화 정보원이 통하는지 | 단독으로는 최강, **추세추종과 결합하면 18~45% 악화** |
| Step 17 워크포워드 | 안정적인 구간이 있는지 | **12구간 중 11구간이 비용을 못 넘음 (p=0.006)** |

이 다섯 줄이 말하는 것은 "우리가 못 찾았다"가 아니라 **"단일 고정 룰로 전 구간·전 심볼을
이기는 것은 애초에 이 시장의 성질이 아니다"** 에 가깝다. 이기는 조합이 있어도 국면이
바뀌면 부호가 뒤집힌다는 것을 세 번(Step 14·15·16) 서로 다른 정보원으로 확인했다.

그래서 문제는 **"어떤 룰이 정답인가"** 가 아니라 **"내 룰이 진짜인지 어떻게 판정하는가"** 다.
그리고 우리는 지난 사흘 동안 정확히 그 판정 장치를 만들어 왔다 — 삼중 배리어 라벨링,
왕복 비용 모델, 워크포워드 12구간 부호 검정, 캔들 캐시, 미래 참조 차단 규칙.

> **전환의 한 문장**
> 우리가 실패한 것은 *상품*(정답지)이지 *설비*(측정 장치)가 아니다.
> 설비를 상품으로 판다.

### 이 전환이 사업적으로도 맞는 이유

1. **적중률 경쟁에서 빠져나온다.** 80%를 못 넘는 승률로 "적중률"을 파는 순간
   경쟁 조건이 우리에게 불리한 숫자 하나로 압축된다. 툴은 그 숫자로 평가받지 않는다.
2. **법률 리스크가 구조적으로 내려간다.** `docs/LEGAL.md` 의 위험 지점은 **유료 BUY/SELL 신호**
   였다. 사용자가 자기 조건으로 과거를 재보는 도구는 "개별성 없는 정보 제공"보다도
   한 단계 더 안전한 쪽에 있다. 우리는 판단을 팔지 않고 **계산기를 판다**.
3. **실패가 자산이 된다.** "우리도 이렇게 여러 번 틀렸고, 그걸 이 도구로 잡아냈다"가
   그대로 제품 설명이 된다. 이건 경쟁사가 복제하기 어려운 종류의 신뢰다.

## 1. 제품 정의

### 1-1. 한 문장

> **가상자산 시장에서 "내 규칙이 진짜인지"를 스스로 판정할 수 있게 하는 백테스팅 워크벤치.**
> 답을 보여주지 않는다. 답을 검증하는 방법을 제공한다.

기존 v2 의 한 문장이 *"매매 판단에 필요한 근거를 제공하는 SaaS"* 였다면,
v3 는 **"매매 규칙을 검증하는 SaaS"** 다. 근거 제공에서 검증 제공으로 한 칸 옮긴다.

### 1-2. 투트랙 — 신호는 유지한다

기존 신호 엔진(Consensus · RuleEngine · AI 설명 · 적중률 추적)을 폐기하지 않는다.
다만 **역할과 위계를 바꾼다.**

| | v2 (현재) | v3 (전환 후) |
| --- | --- | --- |
| 제품의 얼굴 | AI 신호 대시보드 | **백테스팅 워크벤치** |
| 신호 엔진 | 핵심 상품 | ① 부가 상품(무료~BASIC) ② **툴의 프리셋 전략** ③ 우리 자신의 검증 대상 |
| 적중률 화면 | 셀링포인트 후보 | **정직성 증명 장치** — 틀린 것 포함 전부 공개 |
| AI | 신호 설명 | **사용자 요청 시에만 도는 결과 해설기** (§8) |

신호 엔진을 남기는 실질적 이유가 셋 있다.

- **프리셋이 필요하다.** 빈 화면에 지표부터 조립하라고 하면 신규 유저가 이탈한다.
  "Consensus 전략", "추세추종 30일 이평" 같은 **작동하는 출발점**이 있어야 한다.
  우리 룰엔진은 그 프리셋으로 정확히 쓸모가 있다 — 이기지 못해도 **출발점으로는 유효**하다.
- **비교 기준선(baseline)이 필요하다.** 사용자가 만든 전략이 좋은지 나쁜지는 무언가와
  비교해야 안다. Buy&Hold 와 우리 기본 전략 둘을 항상 같이 그린다.
- **이미 만들어져 있다.** 추가 비용이 0 에 가깝다.

> **다만 마케팅 전면에는 신호를 두지 않는다.** `docs/LEGAL.md` 의 금지 표현 목록과
> Step 17 결과(12구간 중 11구간 비용 미달)를 고려하면, 신호를 헤드라인으로 삼는 순간
> 법률 리스크와 신뢰 리스크를 동시에 진다.

## 2. 기본 전제 — 정리와 충돌 해소

사용자가 제시한 5개 전제를 그대로 옮기고, 그중 **서로 충돌하거나 실측과 어긋나는 3건**을
명시적으로 해소한다. 해소하지 않고 넘어가면 구현 단계에서 조용히 잘못된 방향으로 간다.

### 2-1. 원안 (사용자 제시)

1. 각 거래소가 지원하는 **모든 코인** 데이터를 5분봉/시간봉/일봉으로 **적재만** 한다.
   거래소별 각각이 아니라 **코인별**로 모은다. 거래소별 가격은 대동소이하다고 본다.
2. 그중 **한국 거래소 상장 코인에만** 김치프리미엄(+/- %)을 계산해 봉 데이터에 필드로 붙인다.
3. 백테스팅 및 향후 툴은 **사용자가 선택한 1개 거래소 기준**으로만 제공한다.
   단, 김프 계산에는 업비트 값이 필수다.
4. 제공할 툴 4종 — 인디케이터 / 매크로지표 / 파생상품 / 뉴스 + 롱숏 투표.
5. 툴 조합으로 백테스트 → 결과가 나오면 **"AI 분석" 버튼을 눌렀을 때만** AI 해설.

### 2-2. 해소 ① — "코인별 적재" 와 "거래소 선택"은 그대로 두면 모순이다

전제 1 은 *거래소별로 따로 모으지 않는다*고 하고, 전제 3 은 *사용자가 고른 거래소 기준으로
제공한다*고 한다. 코인당 시계열이 하나뿐이면 "거래소를 고른다"는 말이 성립하지 않는다.

**해소: 가격 시계열은 코인당 1개(정본), 거래소 선택은 "가격"이 아니라 "규칙"을 고르는 것으로 정의한다.**

```
코인당 정본 시계열 1개  ←  기준 거래소(reference exchange)에서 수집
        +
업비트 KRW 시계열       ←  김프 계산 및 국내 체결가용 (국내 상장 코인만)
        +
거래소별 메타데이터     ←  상장 유무 · 수수료 · 최소주문 · 견적통화
```

사용자가 거래소를 고르면 바뀌는 것은 셋이다.

| 바뀌는 것 | 내용 |
| --- | --- |
| **유니버스** | 그 거래소에 상장된 코인만 목록에 나온다 |
| **비용 모델** | 그 거래소의 수수료 + 슬리피지로 왕복 비용을 계산한다 (`backtest/costs.py` 확장) |
| **체결 통화·가격** | 업비트 선택 시 KRW 시계열로 체결, 그 외는 USDT/USD 정본 시계열 |

**바뀌지 않는 것: 지표 계산에 쓰는 가격 시계열.** 이건 Step 4-b 에서 이미 내린 결정과
같은 모양이다 — *"신호는 운영과 똑같이 내고, 체결만 업비트 가격·수수료로 한다."*
전제 1 의 "대동소이하다"는 가정을 유지하면서 전제 3 을 만족시키는 유일한 해석이다.

> **정본 거래소 선정 규칙**: 코인마다 다르다. 유동성이 가장 큰 곳을 정본으로 삼되,
> ① binance → ② okx → ③ bybit → ④ coinbase → ⑤ upbit 순으로 상장 여부를 확인해 첫 번째를
> 쓴다. 어느 거래소를 썼는지는 **반드시 봉 데이터에 기록**한다(`source_exchange`).
> 기록하지 않으면 나중에 "이 백테스트 결과가 어디 가격인지" 알 수 없다.

**대안(채택 안 함)**: 거래소×코인×타임프레임을 전부 저장하면 전제 3 을 문자 그대로 만족한다.
저장량이 최대 5배가 되고(§3-3), 무엇보다 우리 실측이 거래소 간 방향 합의율 61~68%,
즉 **대부분 같은 방향**임을 보였다. 5배 비용으로 사는 정보가 그만큼 되지 않는다.
다만 스키마는 `source_exchange` 컬럼을 PK 에 포함해 **나중에 거래소별 저장으로 확장 가능한 형태**로
만들어 둔다. 지금 안 쓴다고 문을 닫지는 않는다.

### 2-3. 해소 ② — 김프를 +/- 이진값으로 만들면 정보가 사라진다

전제 2 의 *"+몇% 일 때는 유, -몇% 일 때는 무"* 를 문자 그대로 구현하면
**우리가 이미 측정해서 확인한 구조를 버리게 된다.**

Step 15 실측(BTC·ETH 일봉 3,267일, 2017-09~2026-09)은 이랬다.

| 프리미엄 분위 | BTC 30일 뒤 | 승률 | ETH 30일 뒤 | 승률 |
| --- | ---: | ---: | ---: | ---: |
| 하위 20% | +6.50% | 59.1% | +10.42% | 64.7% |
| 중간 60% | +5.67% | 57.6% | +4.46% | 51.3% |
| 상위 20% | +0.31% | 39.2% | +4.24% | 42.9% |

**완벽하게 단조적이다.** 이 구조는 "+냐 −냐"가 아니라 **"평소보다 높냐 낮냐"** 에서 나온다.
김프는 장기간 0 보다 위에 머무는 구간이 흔해서, 0 을 기준으로 자르면
상위 20% 와 중간 60% 가 같은 통으로 들어간다 — 위 표에서 가장 정보가 많은 경계가 지워진다.

**해소: 원시값 + 분위수 + 변화율을 모두 필드로 붙이고, 이진 플래그는 그중 하나로만 둔다.**

| 필드 | 정의 | 왜 필요한가 |
| --- | --- | --- |
| `kimp_pct` | `(KRW가 ÷ USDKRW) ÷ USD가 − 1`, 소수 4자리 | 원시값. 모든 파생 필드의 근거 |
| `kimp_pctile_365d` | 직전 365일 분포에서의 백분위 (0~100) | **실측에서 효과가 나온 형태.** 국면 이동을 흡수한다 |
| `kimp_chg_24h` | 24시간 전 대비 `kimp_pct` 변화(%p) | 수준보다 변화가 빠른 신호일 수 있다 (미검증) |
| `kimp_positive` | `kimp_pct > 0` (유/무) | 사용자가 요청한 이진 플래그. **직관적이라 UI 조건으로 유지** |
| `kimp_coin_pct` | `(KRW가 ÷ USDT/KRW) ÷ USD가 − 1` — **코인 프리미엄** | `validation/kimchi.py` 가 이미 두 값을 함께 낸다. 24시간 도는 값이라 주말 공백이 없다 |
| `usdkrw` | 사용한 환율과 그 출처·시각 | 없으면 "프리미엄 변화"와 "환율 변동"이 섞여 값이 무의미해진다 |

> **환율 소스는 실환율이어야 한다.** Step 15 에서 업비트 `USDT/KRW` 로 대체하려다 틀렸다 —
> 그 가격 자체가 이미 김프를 담고 있어 상쇄된다(범위가 ±0.19% 밖에 안 나왔다).
> `frankfurter.app`(ECB 기준, API 키 불필요)를 1차 소스로 쓰고, 한국은행 API 를 예비로 둔다.
> **ECB 기준환율은 평일 하루 한 번이라 주말·공휴일에 값이 없다.** 직전 영업일 값을 이어 쓰되
> (`forward fill`), 그 구간의 프리미엄은 **환율이 고정된 상태의 값**이라는 표시를 필드에 남긴다
> (`usdkrw_stale`). 표시하지 않으면 주말 김프 변동을 실제 변동으로 착각한다.
> 이 한계가 없는 것이 `kimp_coin_pct` 다 — 두 값을 함께 두는 이유가 여기 있다.
> **분위수는 반드시 직전 365일 rolling 으로 낸다.** 전체 이력에서 뽑으면 2018년에 서서
> 2026년 분포를 아는 셈이라 미래를 보는 것이다.

**분위수 계산에는 warm-up 이 필요하다.** 상장 1년 미만 코인은 `kimp_pctile_365d` 가 NULL 이다.
0 이나 50 으로 채우지 않는다 — 없는 값을 지어내면 백테스트가 조용히 거짓말을 한다.

### 2-4. 해소 ③ — 파생상품 데이터는 이력이 짧다. 툴에 넣되 경고를 붙인다

전제 4 의 파생상품 툴(펀딩비 · 미결제약정 · 롱숏 비중)은 **Step 14 착수 전 실측에서
이력 한계가 확인됐다.**

| | 펀딩비 이력 | 미결제약정(OI) 이력 |
| --- | --- | --- |
| binance | 180일+ | **30일** (60일 요청 시 `BadRequest`) |
| bybit | 180일+ | **180일+** ✅ |
| okx | 90일+ | **30일** (60일 요청 시 `ExchangeError`) |

**해소: 툴 목록에는 넣되, 세 가지를 강제한다.**

1. **OI 는 bybit 단일 소스**로 제공한다. OI 는 시장 전체 포지션 지표라 단일 거래소도
   의미가 있다(가격과 달리 거래소 간 합의를 낼 성질이 아니다).
2. **파생 필드를 조건에 넣으면 백테스트 가능 구간이 자동으로 줄어든다.**
   UI 가 이걸 **미리** 보여준다: *"이 조건을 넣으면 검증 가능 구간이 3,267일 → 180일로 줄어듭니다."*
   조용히 줄어들면 사용자는 짧은 표본에서 나온 좋은 숫자를 믿게 된다.
3. **지금부터 3거래소 OI 를 아카이브한다.** 안 하면 30일 이전은 영영 못 받는다.
   `docs/EXTERNAL_DATA.md` 의 원칙 — *"신호에 반영할지는 나중에 정해도 되지만
   모으는 것만은 지금 시작해야 한다"* — 가 그대로 적용된다.

> **참고**: Step 14 는 파생 데이터를 **우리 배점표에** 넣지 않기로 했다. 그건 *우리가 파는 신호*에
> 대한 결정이고, **사용자가 자기 백테스트에 쓰는 것을 막는 결정이 아니다.** 오히려
> "3구간 중 2구간에서만 좋았다"는 우리 측정 결과를 **툴 안의 경고로 노출**하는 것이
> 이 제품의 차별점이다(§7).

## 3. 데이터 계층

### 3-1. 세 개의 창고

성질이 다른 것을 한 테이블에 뭉치면 셋 다 어색해진다. `docs/EXTERNAL_DATA.md` 에서
이미 세운 원칙을 캔들까지 확장한다.

| 창고 | 내용 | 갱신 | 개정되는가 |
| --- | --- | --- | --- |
| **캔들 웨어하우스** | 코인×타임프레임 OHLCV + 김프 필드 | 5분/1시간/1일 | 아니오 (확정 후 불변) |
| **외부 시계열** | 매크로(금리·CPI·고용·환율·유가·금), 파생(펀딩·OI·롱숏) | 소스마다 다름 | **예 — 매크로는 개정된다** |
| **이벤트** | 뉴스(제목·요약·링크), 경제 캘린더, 롱숏 투표 | 상시 | 아니오 |

### 3-2. 시점 정확성(point-in-time)은 타협하지 않는다

모든 레코드에 **사건 시각**과 **우리가 본 시각**을 따로 남긴다.
8월 CPI가 9월 10일에 발표됐다면 **9월 9일 백테스트는 그 값을 몰라야 한다.**
매크로 지표는 개정되므로 `(indicator, ref_date, vintage_date)` 3중 키로 저장하고,
백테스트는 항상 **"그 시점에 알 수 있었던 vintage"** 만 읽는다.

이걸 지키지 않으면 매크로 툴은 **환상을 만드는 기계**가 된다. 사용자가 "CPI 발표 후
하락하면 매수" 전략으로 훌륭한 성적을 얻고, 실전에서 재현되지 않는다.

### 3-3. 규모 산정 — 이게 이번 전환의 가장 큰 신규 비용이다

현재 시스템에는 **캔들 테이블이 없다.** 실시간 수집 후 `.cache/candles` 파일 캐시로만 쓴다.
"모든 코인 적재"는 사실상 새 인프라를 하나 짓는 일이다.

유니버스를 실측 전 추정치로 잡으면(binance USDT 현물 ~500, okx ~300, upbit KRW ~200,
중복 제거 후 **고유 코인 약 800개**):

| 타임프레임 | 코인당 연간 봉 | 800코인 연간 행 |
| --- | ---: | ---: |
| 5분 | 105,120 | 84,096,000 |
| 1시간 | 8,760 | 7,008,000 |
| 1일 | 365 | 292,000 |
| **합계** | 114,245 | **약 9,140만 행/년** |

행당 약 120바이트(OHLCV + 김프 5필드 + 인덱스 오버헤드) 가정 시 **연 약 11GB**.
5분봉을 5년치 소급하면 **누적 50GB 대**로 들어간다.

**저장소 결정: 캔들은 MySQL 에 넣지 않는다.**

| 후보 | 판단 |
| --- | --- |
| MySQL (현행) | 앱 데이터(회원·전략·백테스트 결과·뉴스)에만 쓴다. 억 단위 행 스캔은 이 엔진의 강점이 아니다 |
| **Parquet + DuckDB** ✅ | 백테스트는 "한 심볼 한 구간 전체 스캔" 이 지배적 — 컬럼 저장의 정확한 사용처다. 운영 비용 0(서버 프로세스 없음), Python 네이티브, 파일이 곧 백업. **채택** |
| ClickHouse | 성능은 최상이나 1인 운영에 서버 하나가 더 는다. 동시 백테스트가 병목이 되면 그때 검토 |

레이아웃: `warehouse/candles/tf=5m/symbol=BTC/year=2026/month=09.parquet`
— 심볼·타임프레임·월 파티션. 백테스트가 읽는 건 대개 한 심볼의 몇 달치다.

> **경계선**: 사용자에게 노출하는 유니버스와 실제 적재 유니버스를 처음부터 같게 두지 않는다.
> **Phase 1 은 시가총액·거래대금 상위 100 코인 + 업비트 KRW 전 종목으로 시작한다.**
> 800코인 5분봉 5년을 먼저 채우면, 아무도 안 쓰는 코인 때문에 몇 주를 쓰게 된다.

### 3-4. 소급 한계 — 지금 시작해야 하는 것과 나중에 해도 되는 것

| 데이터 | 소급 가능한가 | 조치 |
| --- | --- | --- |
| 캔들(일봉·시간봉) | ✅ 수년치 | 여유 있을 때 채운다 |
| 캔들(5분봉) | ⚠️ 거래소별 상한 상이. 업비트 200봉/요청 + **구멍 존재** | 페이지네이션 + `trim_to_contiguous()`. 빈 곳을 채우지 않는다 |
| 환율(USDKRW) | ✅ ECB 일별 장기 | 일봉 김프는 즉시 3,267일 확보 가능 (Step 15 에서 실증) |
| 펀딩비 | ⚠️ 90~180일 | 즉시 아카이브 시작 |
| **미결제약정(OI)** | ❌ **30일(binance/okx)** | **최우선 아카이브.** 지금 안 모으면 영영 못 받는다 |
| 뉴스 | ❌ RSS 는 최신 수십 건 | 이미 수집 중(Step 11-a). 계속 돌린다 |
| 매크로 원본 vintage | ❌ 개정 전 값은 복원 난이도 높음 | FRED API 키 확보 후 즉시 시작 |

> **Phase 0 의 진짜 내용은 "수집기를 켜 놓는 것"이다.** 화면보다 먼저 켠다.
> 화면은 나중에 만들어도 되지만 지나간 시간은 못 산다.

### 4-4. 뉴스 + 롱숏 투표

`trading_engine/external/news/` 에 **RSS 수집·분류가 이미 구현되어 있다**(Step 11-a).
여기에 두 가지를 추가한다.

**① 코인별 색인 + 시장 전반 섹션**

```
뉴스 한 건
  ├── symbols_json: ["BTC","ETH"]   ← 제목·요약에서 매칭 (구현됨)
  └── scope: SYMBOL | MARKET        ← 🆕 시장 전반 영향 기사 분리
```

`MARKET` 섹션이 필요한 이유: "연준 매파 발언"은 특정 코인 기사가 아니지만
**모든 코인에 영향을 준다.** 심볼 색인만 있으면 이 기사는 어디에도 안 걸린다.

**② 롱/숏 투표 — 이 제품에서 가장 방어력 있는 데이터**

각 기사에 유저가 롱/숏을 투표한다. 이건 **아무도 갖고 있지 않은 데이터**이고,
시간이 지날수록 우리만 가진 시계열이 된다. 백테스트 필드로 노출한다:
`news_vote_long_ratio`, `news_vote_count`, `news_vote_velocity_1h`.

> **투표 데이터는 이력이 0에서 시작한다.** 서비스 시작 시점부터만 존재하므로
> 백테스트 가능 구간이 극도로 짧다. UI 가 이걸 명시한다. 그리고 초기에는
> 표본이 작아 소수 유저가 값을 흔든다 — **최소 투표 수 미만은 NULL** 로 둔다.
>
> 역설적으로 이 한계가 기능의 가치를 만든다. 지금 시작해야 1년 뒤 자산이 된다.

## 5. 전략 명세와 백테스트 실행

### 5-1. 사용자는 코드를 쓰지 않는다 — 선언형 명세를 조립한다

Pine Script 같은 스크립트 언어를 만들지 않는다. 이유는 셋이다.
① 임의 코드 실행은 보안 문제다. ② 1인 개발이 감당할 범위를 넘는다.
③ 우리 타깃은 **"코딩 없이 검증하고 싶은 사람"** 이다(§시장성 문서 참조).

전략은 **JSON 명세**로 저장한다.

```jsonc
{
  "name": "김프 저평가 + 추세",
  "universe": { "exchange": "upbit", "symbols": ["BTC", "ETH"] },
  "timeframe": "1d",
  "period": { "from": "2019-01-01", "to": "2026-09-01" },
  "entry": {                                  // 조건 트리 (AND/OR 중첩)
    "op": "AND",
    "children": [
      { "field": "kimp.pctile_365d", "cmp": "<=", "value": 20 },
      { "field": "ind.sma(30)", "cmp": "cross_above_by", "target": "price.close" }
    ]
  },
  "exit": {
    "take_profit": { "type": "atr_mult", "value": 3.0 },
    "stop_loss":   { "type": "atr_mult", "value": 1.5 },
    "time_limit":  { "bars": 30 },
    "signal_exit": { "op": "OR", "children": [
      { "field": "ind.sma(30)", "cmp": "cross_below_by", "target": "price.close" }
    ]}
  },
  "position": { "sizing": "fixed_fraction", "value": 1.0, "direction": "long_only" },
  "costs":    { "profile": "upbit", "fee_bps": 5, "slippage_bps": 5 }
}
```

**연산자 목록(고정)**: `>` `>=` `<` `<=` `==` `between` `cross_above` `cross_below`
`rising_for(n)` `falling_for(n)` `pctile_within(n, lo, hi)` `is_true` `is_null`.
이 목록 밖은 지원하지 않는다. 늘리는 것은 쉽고, 줄이는 것은 어렵다.

### 5-2. 실행 규칙 — Step 4 에서 이미 확정한 것을 그대로 승계한다

새로 정하지 않는다. **이미 실측으로 값을 치른 규칙들이다.**

1. **미래를 보지 않는다.** 봉 종가로 낸 조건은 **다음 봉 시가**에 체결한다.
2. **한 봉에서 익절가·손절가에 모두 닿으면 손절이 먼저였다고 본다.** OHLC 로는 순서를
   알 수 없고, 유리한 쪽을 가정하면 백테스트가 부풀려진다.
3. **자본 곡선을 매 봉 기록한다.** 거래 종료 시점만 찍으면 보유 중 낙폭이 MDD 에서 빠진다.
4. **데이터 끝에서 보유 중이면 마지막 종가로 청산**해 지표에 포함시킨다.
5. **구멍 뚫린 시계열은 가장 긴 연속 구간만 쓴다** (`trim_to_contiguous()`).
   빈 곳을 채우지 않는다 — 없는 시세를 지어내는 것이다. 잘린 사실은 결과에 표시한다.
6. **손익비는 손실 거래가 없으면 NULL.** 0 으로 채우면 "손실이 없었다"가 "손익비 0"으로 읽힌다.
7. **모르는 비용 프로파일은 예외로 막는다.** 참고용으로 물러서면 잘못된 비용으로
   "수익이 났다"는 결과가 조용히 나온다.

### 5-3. 실행 인프라

```
사용자 "실행"  →  전략 JSON 검증  →  가용 구간 계산  →  작업 큐(Redis)
                                                            ↓
                                          워커(backtest/worker.py, 구현됨)
                                                            ↓
                                          DuckDB 로 Parquet 스캔 → 벡터화 평가
                                                            ↓
                                          결과 저장(backtest_logs, 확장) → 화면 푸시
```

**성능 목표와 근거**: Step 4 실측은 475봉×4거래소 재생에 약 16초였다 — 봉마다 거래소별
지표를 다시 계산했기 때문이다. v3 는 **지표를 미리 계산해 열로 저장**하므로(사전 계산 캐시)
같은 규모가 1초 미만이어야 한다. 일봉 3,000봉 단일 심볼은 **즉시(<0.5초)**,
5분봉 1년(105,120봉) 10심볼은 **10초 이내**를 목표로 잡는다.

**등급별 제한**: 무료 하루 N회 / 최대 구간·심볼 수 제한. 백테스트는 CPU 를 먹는다.
제한이 없으면 한 명이 서버를 점유한다.

## 7. 과최적화 방지 — 이게 제품이다

여기가 **이 기획서의 중심**이다. 백테스팅 도구는 이미 많다. 없는 것은
**"당신의 좋은 결과가 우연일 확률"을 정직하게 말해 주는 도구**다.

우리는 그 계산 방법을 **이미 만들었고, 그 도구로 우리 자신의 전략을 세 번 기각했다.**
이보다 나은 제품 서사는 없다.

### 7-1. 항상 켜져 있는 5개 장치

| 장치 | 무엇을 하나 | 근거 (우리 이력) |
| --- | --- | --- |
| **① 왕복 비용 강제 표시** | 거래당 기대값 옆에 항상 왕복 비용을 나란히 놓는다. 기대값 < 비용이면 결과 전체를 회색 처리 | Step 4: *"비용이 기댓값을 통째로 먹는다"* |
| **② 워크포워드 12구간 부호 검정** | 결과와 동시에 자동 실행. 비중첩 구간 중 몇 개가 양수인지 + 이항검정 p값 | Step 17-a 에 **이미 구현됨** |
| **③ 구간별 성적 표** | 국면마다 부호가 뒤집히는지 눈으로 보게 한다 | Step 14·15·16 전부 이 문제로 기각 |
| **④ 시도 횟수 카운터** | "이 심볼에서 당신의 N번째 조합입니다." N 이 커질수록 다중검정 보정을 강하게 적용 | 앞선 조합 탐색 96개가 **전부 in-sample** 이었던 우리 실수 |
| **⑤ 표본 충분성 경고** | 거래 수 < 30, 또는 구간 < 1년이면 결론 표시를 억제 | Step 4: *"2일·심볼당 10여 건은 표본이 작다"* |

### 7-2. 시도 횟수 카운터 — 아무도 안 하는 기능

경쟁 서비스는 사용자가 100개 조합을 돌려 가장 좋은 하나를 고르는 것을 **그냥 둔다.**
그게 정확히 p-해킹이고, 그렇게 고른 전략이 실전에서 죽는 이유다.

우리는 **세션별로 사용자가 같은 심볼·기간에서 시도한 횟수를 센다.**

```
N=1   결과 그대로 표시
N=10  "10개 조합 중 최고를 고르면, 무작위여도 이 정도 성적이 하나쯤 나옵니다"
N=30+ 다중검정 보정 후 유의성 재표시 + 홀드아웃 구간 강제 권유
```

**홀드아웃 잠금**: 사용자가 기간을 설정할 때 **최근 20%를 자동으로 잠근다.**
잠긴 구간의 결과는 사용자가 "최종 검증" 버튼을 눌러야 딱 한 번 열린다.
연 것은 기록에 남고, 그 뒤로는 그 심볼에서 잠금이 소진된다.

> 이건 사용자를 불편하게 만드는 기능이다. 그리고 **그 불편이 곧 제품의 정직성**이다.
> "결과가 좋게 나오는 도구"는 널려 있다. "결과를 믿어도 되는지 말해 주는 도구"는 드물다.

### 7-3. 우리 실패를 공개 자산으로 만든다

`ROADMAP.md` 의 Step 14·15·16·17 측정을 **"검증 아카이브"** 로 제품 안에 공개한다.

```
검증 아카이브
├─ 파생 데이터(OI·펀딩비)는 배점에 도움이 되는가 → ❌ 표본 18,683건, 부호 반전
├─ 김치 프리미엄 단독 효과                      → ✅ 단조적 (3,267일)
├─ 김치 프리미엄 + 추세추종 결합                → ❌ 0.55~0.82배 악화
└─ 배점표 v3 (RSI·볼린저 가중)                  → ❌ 시기마다 부호 반전
```

각 항목은 **원클릭으로 해당 전략을 워크벤치에 로드**한다. 사용자는 우리 실패를
직접 재현하고 자기 변형을 시도할 수 있다. 이것이 §1-2 의 "프리셋"이 실제로 쓰이는 방식이다.

## 8. AI 분석 — 버튼을 눌렀을 때만

### 8-1. 자동 호출하지 않는 이유는 비용만이 아니다

전제 5 의 "버튼" 설계에 전적으로 동의한다. 이유가 셋이다.

1. **비용.** 봉마다·실행마다 호출하면 백테스트 한 번에 수천 건의 유료 호출이 난다.
   Step 4 가 같은 이유로 백테스트에서 AI 를 뺐다.
2. **오염.** 자동으로 해설이 붙으면 사용자는 **숫자보다 문장을 먼저 읽는다.**
   우리가 만들려는 건 사용자가 스스로 판단하는 도구다.
3. **책임.** `docs/LEGAL.md` — AI 가 자동으로 "이 전략은 좋습니다"라고 말하면
   그건 투자 조언에 가까워진다. **사용자가 요청한 해설**은 성격이 다르다.

### 8-2. AI 가 하는 일 / 하지 않는 일

| 한다 ⭕ | 하지 않는다 ❌ |
| --- | --- |
| 결과 숫자의 **구조**를 설명 (승률은 높은데 손익비가 낮은 이유 등) | "이 전략을 쓰세요" / "실전 투입 가능합니다" |
| **왜 특정 구간에서 부호가 뒤집혔는지** 국면 가설 제시 | 미래 수익률 예측 |
| 과최적화 징후 지적 (거래 수 부족, 파라미터 민감도) | 파라미터를 대신 튜닝 |
| **다음에 무엇을 측정하면 되는지** 실험 제안 | 코인 추천 |

**입력은 결과 요약만 준다** — 봉 데이터 전체를 주지 않는다.
전략 명세 JSON + 지표 5종 + 워크포워드 구간별 성적 + 시도 횟수. 토큰이 예측 가능해진다.

**예산 제어**: `trading_engine/strategy/ai_budget.py` 가 **이미 있다**(Step "AI 예산과 데이터
수집 분리"). 등급별 월 호출 한도로 그대로 쓴다.

| **조건 빌더 UI** | **대** | 제품의 얼굴 |
| 김프 필드 **적재 파이프라인** (분위수·변화율·warm-up) | **소~중** | 계산은 `validation/kimchi.py` 에 있다. 필요한 것은 **웨어하우스에 열로 굽는 일** |
| 매크로 수집기 (FRED, vintage) | 중 | API 키 필요 |
| 파생 아카이버 (펀딩·OI·롱숏) | 중 | **지금 켜야 함** |
| 롱숏 투표 | 소 | |
| 시도 횟수·홀드아웃 잠금 | 소 | 로직은 단순, 설계가 핵심 |
| AI 분석 버튼 + 프롬프트 | 소 | 예산 제어 재사용 |

> **거칠게 보면 신규 개발의 75%가 세 덩어리(웨어하우스 · DSL · 빌더 UI)에 몰려 있다.**
> 나머지는 기존 자산 위에 얹는 수준이다. 이 셋을 얼마나 좁게 시작하느냐가 일정을 결정한다.

## 11. 단계별 로드맵

**날짜를 두지 않는다.** `ROADMAP.md` 의 원칙 그대로 — 지켜지지 않았고 의미를 잃었다.
스텝 간 의존만 정한다.

### Phase 0 — 수집기부터 켠다 (화면보다 먼저)

> 지나간 시간은 못 산다. 이 Phase 의 산출물에 화면은 하나도 없다.

- [ ] **파생 아카이버 가동** — 펀딩비 3거래소 + OI 3거래소 + 롱숏 비율. **최우선**
- [ ] **환율 수집** (frankfurter.app, ECB) — 일별 장기 + 매일 갱신
- [ ] **FRED API 키 확보** 후 매크로 수집기 가동 (vintage 3중 키)
- [ ] 뉴스 RSS 계속 가동 (이미 돌고 있음) + `scope` 컬럼 추가

### Phase 1 — 웨어하우스 (좁게 시작)

- [ ] 유니버스 실측 — 거래소별 상장 코인 수와 겹침을 **실제로 센다**(§3-3 은 추정치다)
- [ ] 정본 거래소 선정 규칙 구현 + `source_exchange` 기록
- [ ] **상위 100 코인 + 업비트 KRW 전 종목**, 일봉·시간봉 전 이력 백필
- [ ] 5분봉은 **최근 1년만** 먼저. 구멍 처리(`trim_to_contiguous`) 적용
- [ ] 김프 5필드 파이프라인 (국내 상장 코인 한정)
- [ ] 정합성 점검 — 봉 수·구멍·중복 자동 리포트

### Phase 2 — 워크벤치 최소 기능 (첫 사용 가능 버전)

- [ ] 전략 명세 JSON 스키마 확정 + 검증기
- [ ] 조건 컴파일러 (인디케이터 + 김프 필드만. 매크로·파생·뉴스는 아직)
- [ ] 조건 빌더 UI + 차트 + 결과 패널
- [ ] **§7 의 5개 장치를 처음부터 함께 넣는다** — 나중에 붙이면 안 붙는다
- [ ] 프리셋 3종 (Buy&Hold / 추세추종 30일 이평 / Consensus 룰엔진)
- [ ] **본인이 먼저 쓴다.** 2026-09-04 "관리자 우선" 결정을 v3 에도 적용

### Phase 3 — 툴 확장

- [ ] 검증 아카이브 (§7-3)

### Phase 4 — 상품화

- [ ] 등급·제한 (§12)
- [ ] 결제 (법률 확인 선행)
- [ ] 다국어 ko/en/ja

### 착수 전 반드시 처리할 것

- **유니버스 실측이 Phase 1 의 착수 조건이다.** §3-3 의 800코인·11GB 는 추정이다.
  실측 결과가 2배면 저장 전략을 다시 본다.

## 14. 열린 질문 — 결정이 필요한 것

1. **유니버스 범위.** 정말 800코인 전부인가, 아니면 상위 100 + 업비트 전 종목으로
   충분한가? (§3-3 은 후자를 권한다)
2. **5분봉 소급 깊이.** 1년? 3년? 저장 비용이 여기서 결정된다.
3. **전략 공개(커뮤니티) 시점.** Phase 4 로 두었으나, 초기 유저 확보에는 이게 가장 강한
   장치일 수 있다. 다만 "잘 나온 전략 자랑"이 되면 §7 의 정직성 설계와 정면으로 충돌한다.
   → **공개 전략은 워크포워드 결과와 시도 횟수를 반드시 함께 노출**하는 조건이라면 가능.
4. **v2 신호 서비스의 유저 노출 여부.** 현재 "관리자 우선" 결정으로 동결 상태다.
   v3 출시 시점에 함께 열 것인가, 계속 동결할 것인가.
5. **거래소 데이터 약관.** 이 답에 따라 §3 전체가 바뀔 수 있다. **가장 먼저 확인할 것.**
